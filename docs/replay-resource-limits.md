# Replay resource limits

Session replay collection is public when an administrator enables it for a website. A signed tracking cache token identifies the visit, but it is not an authorization boundary for allocating unlimited storage or playback memory.

The collector now reserves capacity in PostgreSQL inside the same collection transaction before persisting a chunk. Each visit is limited to 2,048 chunks, 8 MiB of serialized event JSON, and 20,000 raw events. The chunk count supports the configured one-hour maximum at the recorder's ordinary two-second flush interval, while the independent byte and event limits can end a busy recording earlier. Each website is also limited to 32 MiB, 10,000 chunks and 100,000 raw events per UTC minute, and 1 GiB, 1,000,000 chunks and 5,000,000 raw events per UTC day. Count limits prevent tiny events from bypassing the byte budget. These limits apply even when replay events are stored in ClickHouse or sent through Kafka. Explicit chunk timestamps are idempotent within a visit. Requests without a timestamp keep their previous non-idempotent behavior and still consume capacity. A visit limit returns 413; a website window limit returns 429 with `Retry-After`. Heatmap collection is unchanged.

Playback also bounds the number of chunks and cumulative stored, decoded, and event data before merging or reconstructing fragments. PostgreSQL's compressed storage has a separate 1 MiB allowance for gzip overhead beyond the 8 MiB decoded limit; ClickHouse's plain JSON storage uses the 8 MiB limit. A replay that predates these intake limits and exceeds the safe playback budget returns 413. Its data is retained rather than deleted or silently truncated. Ordinary replays below the limits remain readable.

The `29_bound_replay_ingestion` migration adds only the `replay_ingest_budget` table and index. It does not rewrite historical migrations, modify existing replay rows, or impose a retention policy. Apply the migration through the guarded database workflow before starting this source release. Per-visit accounting is durable while the website and its replay data remain; expiring it would allow an old visit ID to exceed its quota. Only expired minute/day accounting rows are removed in bounded batches during accepted replay writes. Website deletion cascades to its accounting rows. Existing replay storage and its accounting rows still need normal capacity monitoring and a separately reviewed retention policy.

These are source and artifact controls, not proof of production activation. Rehearse the exact packaged runtime, existing database migration ledger, new and old replay behavior, and rollback on the target host. A rollback to a release without these controls reopens the replay-ingest path; retain the prior artifact for recovery but assess that security tradeoff before activating it. If a deployment uses ClickHouse or Kafka, validate its exact storage/query path independently before promotion.
