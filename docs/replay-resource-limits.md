# Replay resource limits

Session replay collection is public when an administrator enables it for a website. A signed tracking cache token identifies the visit, but it is not an authorization boundary for allocating unlimited storage or playback memory.

The collector now reserves capacity in PostgreSQL inside the same collection transaction before persisting a chunk. Each visit is limited to 2,048 chunks, 8 MiB of serialized event JSON, and 20,000 raw events. The chunk count supports the configured one-hour maximum at the recorder's ordinary two-second flush interval, while the independent byte and event limits can end a busy recording earlier. Each website is also limited to 32 MiB, 10,000 chunks and 100,000 raw events per UTC minute, and 1 GiB, 1,000,000 chunks and 5,000,000 raw events per UTC day. Count limits prevent tiny events from bypassing the byte budget. These limits apply even when replay events are stored in ClickHouse or sent through Kafka. Explicit chunk timestamps are idempotent within a visit. Requests without a timestamp keep their previous non-idempotent behavior and still consume capacity. A visit limit returns 413; a website window limit returns 429 with `Retry-After`.

The recorder sends replay and heatmap navigation URLs with only origin and pathname, omitting credentials, query strings, and fragments. The server repeats this for ordinary replay events before storage and for historical replay responses, including reassembled fragments. Path segments and other recorded page content are not redacted by this URL rule; tracked sites should not put secrets in URL paths or unmasked page content.

The authenticated replay API also removes browser-fetchable resource URLs from restored snapshots and later DOM/CSS changes before returning events to a viewer. External images, stylesheets, fonts, embedded documents, and CSS imports or URL references do not load in the viewer's browser; safe inline raster images and non-resource layout/text remain. This applies to historical and fragmented recordings as well as new ones. A replay may therefore omit externally hosted visual assets rather than making requests to the recorded site or a third party with the viewer's browser credentials. Collection and stored event bytes are not rewritten by this playback rule.

Playback also bounds the number of chunks and cumulative stored, decoded, and event data before merging or reconstructing fragments. PostgreSQL's compressed storage has a separate 1 MiB allowance for gzip overhead beyond the 8 MiB decoded limit; ClickHouse's plain JSON storage uses the 8 MiB limit. A replay that predates these intake limits and exceeds the safe playback budget returns 413. Its data is retained rather than deleted or silently truncated. Ordinary replays below the limits remain readable.

Heatmap intake uses the same durable PostgreSQL budget table with separate heatmap keys. Each visit is limited to 128 requests, 5,000 rows and 4 MiB of serialized event JSON. Each website is limited to 5,000 requests, 20,000 rows and 8 MiB per UTC minute, and 100,000 requests, 500,000 rows and 256 MiB per UTC day. These reservations apply to PostgreSQL, ClickHouse and Kafka sinks. PostgreSQL writes share the collection transaction. External writes start only after the budget transaction commits, then recheck that the website and heatmap collection are still enabled. An exhausted visit returns 413; an exhausted website window returns 429 with `Retry-After`.

Accepted replay and heatmap requests also charge the existing collection account budgets inside the same PostgreSQL transaction. Their serialized bytes and raw event counts contribute alongside ordinary analytics events, limiting aggregate intake across every website owned by one user or team. Recorder-specific website limits remain separate. A previously accepted idempotent replay chunk does not consume another account charge. An exhausted account window returns 429 before any recorder write.

Replay and heatmap intake share an additional per-website limit of 2,000 newly seen visit keys per UTC minute and 50,000 per UTC day. This is separate from byte, event and request limits, and is reserved atomically only on the first accepted chunk for a visit key. An exhausted new-key window returns 429 with `Retry-After`. Its minute/day accounting rows expire and are removed by the same bounded cleanup as other window rows.

Across all websites, each owning user or team can also create at most 5,000 new recorder visit keys per UTC minute and 50,000 per UTC day. These owner counters use separate keys in the existing collection budget table, so normal event traffic does not consume the new-visit allowance. Both owner and website reservations roll back together if any budget or recorder write fails.

The `29_bound_replay_ingestion` migration created the budget table without visit-row expiry. The forward-only `32_expire_replay_visit_budgets` migration gives existing visit-budget rows with NULL expiry 38 days from migration while preserving their counters and chunk indices. New accepted replay and heatmap reservations set or extend a 38-day visit-budget expiry; accepted recorder writes remove expired budget rows in bounded batches. An expired visit key can start a new accounting window, while the separate per-website minute and day limits still apply. This expires accounting state, not stored replay or heatmap data. Apply the migration only through the guarded database workflow after a protected backup, restore rehearsal, and retained-runtime recovery review. A pointer-only rollback is unsafe if the retained runtime rejects the new migration ledger entry. Do not rewrite historical migrations or live ledger rows.

These are source and artifact controls, not proof of production activation. Rehearse the exact packaged runtime, existing database migration ledger, new and old replay behavior, and rollback on the target host. A rollback to a release without these controls reopens the replay-ingest path; retain the prior artifact for recovery but assess that security tradeoff before activating it. If a deployment uses ClickHouse or Kafka, validate its exact storage/query path independently before promotion.
