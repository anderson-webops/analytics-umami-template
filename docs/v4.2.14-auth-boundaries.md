# v4.2.14 authentication and annotation boundaries

This template release corrects three source-level security findings. It does not
change historical migrations, database ledgers, listener ports or production
configuration. Propagate the template commit into compatible analytics forks;
preserve their site-specific configuration and migration contracts.

- API-key permission checks resolve team-navigation prefixes as well as the
  existing base-path and relative API aliases before classifying restricted
  account routes. Data and ordinary team APIs retain their existing permissions.
- Both annotation read endpoints require a matching share, filtering permission,
  and an enabled Overview or Compare section. Legacy sectionless and board shares
  remain supported. Independently authorized owners, administrators and team
  members retain access. An unrelated signed-in user cannot expand share access.
- Local password login always reads authoritative primary two-factor enrollment. Cloud-mode accounts
  with enabled local two-factor authentication receive a bounded 503 without a
  token, session, cookie or password rehash because Cloud mode cannot complete
  the local challenge. Use the configured Cloud sign-in flow; do not remove
  enrollment to bypass this gate. Unenrolled Cloud password login and self-hosted
  two-factor challenges retain their existing behavior.

Regression tests exercise the actual annotation read handlers with synthetic
identity and persistence fixtures, the shared API-key guard, and both Redis and
stateless login modes. Production activation, site-specific privacy acceptance
and retained-runtime recovery remain separate operator gates.

The focused HTTP regression uses only a disposable loopback application with
synthetic PostgreSQL data and its administrator password in
`API_TEST_ADMIN_PASSWORD`. Run it through the existing API command:
`pnpm test:api --coverage-report -- -c tests/api/auth-boundaries.config.ts`.
It verifies annotation list/detail permissions and legitimate owner/API-key
access without relying on the full analytics-ingestion seed. The wider API
suite currently stops in its unrelated secondary-website seed because it
supplies a custom entity ID as a non-administrator; the application restriction
remains unchanged. This focused result is not a claim that the wider suite passes.

The dependency graph pins `fast-uri` 3.1.8 and `brace-expansion` 5.0.12 to address
the advisories present in the September 29 registry audit. Both full and
production-only audits remain mandatory, without exclusions or lower thresholds.
