# Tracking URL privacy

The browser tracker and `/api/send` collector remove URL credentials and fragments before sending or storing page activity. The collector applies the same policy to direct, batched, link and pixel events, so a caller cannot restore private URL components by bypassing the tracker. Referrer queries are never retained.

Page queries retain only `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term`, `gclid`, `fbclid`, `msclkid`, `ttclid`, `li_fat_id`, `twclid`, `ad_id`, `aid`, `dclid`, `epik`, `ob_click_id`, `pc_id`, `rdt_cid` and `scid`. Each value must be a simple attribution label or identifier of at most 255 characters; nested URLs, encoded delimiters and control characters are rejected. The encoded allowlisted query is capped at 500 characters. Other query keys and values are discarded, including common password-reset, authorization-code and session parameters. `data-exclude-search="true"` removes even the approved attribution query from browser events; the collector still enforces its allowlist for direct requests. Fragments are always removed, including when an older script sets `data-exclude-hash="false"`.

This deliberately changes full-path grouping when it previously depended on arbitrary query strings or hash routes. Hash-only history transitions still count as pageviews, but their stored URL omits the fragment. Approved UTM and click identifiers remain available for attribution and paid-channel reports. A site using a hash router should send a separately reviewed, non-sensitive route name as a custom event rather than putting private fragment content in a page URL. Do not treat a custom event payload as an automatically sanitized page URL. The approved attribution keys can still contain a site-supplied secret-shaped simple value; avoid putting credentials in those parameters.

Previously stored analytics data is not rewritten or purged by this source change. Any historical cleanup requires a separate backed-up retention or migration review with recovery testing.

Website sessions no longer derive an anonymous replay identity from a shared IP address and User-Agent. After tracking is permitted, the browser tracker creates a cryptographically random session seed and keeps it in first-party `sessionStorage` across page loads. The collector uses that seed to derive a website-scoped session, but does not write the raw seed to event or replay rows. A newly opened same-origin tab rotates a seed copied from its live opener; browser duplicate-tab features without an opener can still copy session storage, so this is not a guarantee of distinct replay streams across every tab. Withdrawing tracking permission clears the stored seed when the tracker next checks that setting. Each site must retain its own consent and recorder policy before enabling collection.

When browser storage is unavailable, the seed lasts only for the current page; a client without a seed or a valid current cache token receives a fresh random session. Batch collection reuses a token only for the same website, seed, and explicit identity. Pre-change cache tokens are rejected for replay writes; a previously loaded recorder may stop sending until its tracker obtains a new token or the page reloads. Anonymous visitor and session counts may change, and already merged replay rows cannot be reliably separated by this release.

Replay snapshots and mutations discard URL-bearing DOM attribute values before transmission and again before storage. Only the supported URL-change and scroll-progress custom replay events are retained; their fields are rebuilt from bounded, sanitized values. Strict replay masking still depends on the site's reviewed recorder configuration. Existing replay rows are not retroactively changed.
