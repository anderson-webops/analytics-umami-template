# Collector authorization transition

This template change is a breaking collector contract. It is source work, not production activation. Review the existing site integrations, retained runtime, runtime configuration, and rollback before publishing or promoting it. Do not connect from this checkout to the production server.

## Default behavior

- Ordinary pageviews, link hits, pixel hits, and performance observations remain unverified, rate-limited collection. The latter three preserve existing public counting and performance behavior; none authorizes an identity, custom event, revenue claim, or recording. A browser-supplied identity is rejected, not written as a pageview property. The bundled tracker neither attaches `id` to ordinary pageviews nor automatically sends `data-distinct-id`. Browser-chosen session seeds only group unverified observations and must never be treated as proof of identity.
- Client-supplied timestamps require a website-scoped backend credential. Pageviews and performance submissions require its event scope; identify retains its identity scope. Anonymous observations use server receipt time; link and pixel submissions cannot be backdated. A credential authorizes backdating, not a verified visitor identity: historical pageviews remain unverified observations. Historical imports must use a reviewed server-side website integration, not a public tracking URL or browser credential.
- Public website cache tokens carry the current collection generation, which the budget admission reads under the database source lock. A token without that field remains usable only for generation zero. After a website domain or owner change, reset, deletion, or same-ID recreation, a stale token is discarded, and stable browser and backend session seeds derive different session IDs in the new generation. Reset also invalidates previous backend collection keys and recorder permits; a new website-scoped key must be provisioned before advanced tracking resumes. The write lock checks the generation again before persistence; a race returns `409` without writing an event. A later request rechecks the source; do not blindly replay a backend request with a reserved ID. Recorder-permit minting and recorder writes reject stale public cache tokens even with a new backend credential. Keep the tombstone and generation state through backup and rollback; a source release alone does not prove that protected state is preserved.
- `identify`, named custom events, and event properties require a website-scoped backend credential at `/api/send`; `/api/batch` applies the same check separately to every item. Their session IDs are derived in a separate server-only namespace, never from an anonymous cache token, and their responses contain no browser-reusable cache token. A backend may supply its own stable session seed or verified user identity to group its submissions. An ordinary pageview cannot carry `id`, even with backend proof; use a separate `identify` request. Public website IDs, allowed origins, cache tokens, and browser session seeds are not credentials.
- Anonymous sends reserve separate source and owner minute/day budgets below the shared circuit breakers; authenticated website-backend sends skip only those anonymous budgets, never the per-client or shared limits. Backend and anonymous client-budget keys occupy separate namespaces even behind the same trusted-edge IP. The anonymous source minute request cap is one quarter of the reviewed shared source limit. A bearer header on a public pageview does not elevate it to backend admission. This reserves source/owner quota, not guaranteed service: the shared pre-auth IP cap and global rate-limit key pool can still reject requests. Review actual traffic against the proposed anonymous ceilings before activation, and keep the trusted edge's `CLIENT_IP_HEADER` contract intact.
- Revenue-bearing fields at any nesting level are rejected at the public collection route and internal event/property write boundary, even with a backend credential. A separate, default-off server-to-server movement endpoint writes only to an isolated PostgreSQL attestation ledger; it does not turn browser claims into verified orders or feed the historical revenue reports. The guard also rejects property names containing `revenue` without a word separator because the historical PostgreSQL import and ClickHouse materializer match that substring. Unrelated `concurrency` properties remain usable. The former direct PostgreSQL revenue writer is removed; existing revenue rows are retained and are not reclassified as verified.
- The optional browser test console offers only public pageviews. Its former browser identity, custom-event, revenue, and recorder controls were removed because those submissions cannot satisfy the separate backend-proof and consent requirements.
- This unpublished candidate adds a `session_data.trust_tier` column in PostgreSQL and ClickHouse. Historical rows default to 0; backend-authorized identity properties are written as 1. Derived session-property reports and filters use only tier 1, while direct session-property reads and their API schema expose the tier, and the session detail view labels unverified rows. Tier 1 means the website backend authorized submission, not that its claimed identity or business facts are independently true. Both migration files are required by the runtime artifact and ClickHouse readiness checks for the column. The independently maintained ClickHouse/Kafka consumer must still be verified to preserve this field before release. Existing rows are retained, not upgraded.
- The forward-only `session_link.trust_tier` migration leaves historical identity links at tier 0. Only a new backend-authorized identify request creates or upgrades a PostgreSQL link to tier 1. Session detail and activity discover linked identities through those tier-1 rows in either storage mode; they do not fall back to a historical session's `distinct_id` or traverse legacy ClickHouse links. Legacy ClickHouse rows remain for bounded admission accounting, not identity authority. A directly selected historical session remains readable, but its unverified identity is not presented as verified or used to join other sessions. Test retained-row preservation, re-authorization, link caps, and both storage modes on synthetic copies before any migration. This boundary does not validate the external Kafka consumer or its historical backlog.
- Direct, numbered, and saved-cohort `distinctId` filters consult canonical tier-1 PostgreSQL links in either storage mode. Negative filters exclude a session if any of its verified identities matches the excluded value. ClickHouse resolves at most 2,000 matching session IDs per filter and rejects broader matches instead of truncating them. PostgreSQL identity-value discovery and metric projections now use verified links. Session-summary queries no longer project raw identity labels in either mode; the session-detail route supplies only a uniquely verified link. A disposable cross-store test exercises the ClickHouse identity filter and link-delivery recovery. A separate disposable PostgreSQL 17 and ClickHouse 25.8 test now verifies identity-value discovery and metric projections against canonical links while raw ClickHouse rows carry a forged identity label. These tests do not verify every report path, the independent Kafka consumer, or production data.
- The draft event migration adds `trust_tier` to `website_event` and `event_data`. Historical rows default to 0, and new custom events plus their properties are marked 1 only after backend proof. Derived custom-event reports now require tier 1; direct history reads retain older rows with an explicit unverified label. ClickHouse event/session reports use raw rows rather than the mixed-tier hourly aggregate, and a new verified property pivot accepts only tier-1 children while its reads also require a tier-1 parent. The direct ClickHouse writer inserts properties before publishing the trusted parent, so a failed property insert cannot leave a countable tier-1 event. A failed parent insert can leave orphan properties; property reports and the exported usage helper require a tier-1 child with a tier-1 parent. Disposable ClickHouse 25.8 tests apply the exact pivot migration, check same-name verified and unverified rows, orphan children, duplicate parents, property-first visibility, and usage counts. A separate row-preservation test rejects excessive child rows rather than losing them during a planner-reversed `ANY INNER JOIN`. Kafka topic send order does not prove consumer commit order or atomicity; the independent consumer, retained backlog, and protected production-copy migration and recovery remain unverified. Tier 1 denotes backend authorization, not independent truth of the submitted facts.
- Summary traffic now exposes `unverifiedViews` alongside total `pageviews` in both stats endpoints, the generated client, and the read-only MCP tool. Every page, link, and pixel observation remains unverified even if a stored row carries another trust tier, because the supported collector has no verified-view contract. The dashboard retains its localized Views label instead of showing a redundant second total or a false zero against an older API. The MCP tool returns `null`, not a fabricated zero, if an older API omits the field. Other traffic reports still need a provenance review before the overlapping public-collector findings can be considered resolved.
- Historical event-derived revenue has no stored trust tier or verified-order idempotency contract. Historical revenue reports remain available only as labeled unverified claims; the summary returns `arpu: null` rather than divide those claims by anonymous sessions. The UI, API, and MCP descriptions call event and session counts what they are, not orders or customers. Every historical revenue response carries `X-Revenue-Provenance: unverified_historical_event_claims`; object responses and nonempty metrics rows also expose `revenueProvenance` in JSON, while empty metrics arrays retain their existing shape and carry the header. The generated API client returns JSON bodies, not response headers, so an empty metrics result has no claim value to classify through that client. The MCP result carries an explicit marker while suppressing legacy ARPU fields even when an older API returns them. This presentation change does not authenticate legacy rows or prove the independent consumer cannot write directly. The separate attested movement ledger is not a verified-order report: PostgreSQL and ClickHouse/Kafka still need independently supported payment evidence, authoritative refund rules, and separate reporting before a trusted revenue metric can exist. Any live migration also needs protected-copy rehearsal and a database-aware recovery plan because the retained runtime may reject the new migration ledger.
- The draft forward-only PostgreSQL migration `40_add_attested_revenue_movement` creates a separate, immutable capture-only ledger with a website-scoped movement key and deletion coverage. Unsupported refunds are rejected at the request, helper, and database boundaries until a reviewed capture-reference and cumulative-limit contract exists; captures alone are not net revenue. The key cannot be reused under another source label for the same website. A separate `POST /api/revenue/movements` endpoint is disabled unless `REVENUE_ATTESTED_INTAKE_ENABLED` is explicitly enabled. It requires a current owner- and generation-bound website backend key with `revenue` scope, a fresh request nonce/timestamp, strict bounded financial facts, and source-rate admission. Both HTTP and database entrypoints restrict movement timestamps to millisecond precision so changed sub-millisecond claims cannot alias an existing retry. Identical retries return the original movement; changed facts conflict even when the source label, key generation, or amount changes. The movement ID remains unique after the 15-minute nonce window. Disposable PostgreSQL 17 tests check migration, concurrent retries, nonce reuse, conflicts, immutability, invalid values, and site-isolated deletion. The website backend must first verify the order/payment; the credential authenticates the sender but does not independently prove settlement. The route returns `backend_attested`, does not populate historical revenue reports, and must stay disabled until a reviewed site integration and protected recovery rehearsal exist. Payment verification, authoritative refund rules, and separate reporting remain required before any value can be called verified revenue.
- The draft ClickHouse migration `18_disable_unverified_revenue_materialization.sql` removes the legacy event-data-to-revenue view. It preserves the revenue table and prior rows but stops new automatic revenue materialization, matching the denied collector path. Readiness now fails if that exact legacy materialization view still exists in the configured ClickHouse database or if the required verified-property materialization view is absent or has the wrong engine; a packaged migration alone cannot establish either condition. The independent schema probes run concurrently within the bounded readiness deadline. Production intake must verify the retained view, quiesce ingestion, and test the migrated copy plus exact rollback behavior. An independently maintained Kafka consumer must be reviewed for direct revenue writes; this migration alone cannot constrain them. Future verified-order collection needs a separate forward-only contract.
- The draft Kafka sender rejects oversized messages before sending any part of that call and reports send failures or absent acknowledgements as errors rather than successful collection. This does not make the event and property topics atomic or prove that the independent consumer persisted them. A partially acknowledged multi-batch or multi-topic write can still require reconciliation; do not enable trusted collection over Kafka before the consumer and idempotency contract are reviewed.
- The supported guarded production launcher rejects a configured Kafka producer for this candidate. This is a deliberate incompatibility gate, not evidence that the external consumer, retained backlog, or historical ClickHouse rows are safe. Keep any Kafka-configured serving release unchanged until the operator reviews those components and a separately validated producer-consumer transition is available. PostgreSQL-only production collection remains eligible for its other acceptance gates.
- Replay and heatmap collection require an active website recorder setting and a separate 60-second permit bound to website, session, visit, feature, approved HTTPS origin, consent assertion, and an active recorder key. Replay additionally requires strict masking. No recorder script capture starts without a site-owned permit endpoint. The browser masks replay text, attributes, URLs, and unrecognized fields before sending; the server independently masks them before PostgreSQL or ClickHouse/Kafka persistence and again after restoring historical fragments for playback. Strict mode sacrifices some replay visual fidelity. Historical stored bytes remain unchanged and require separate protected retention review; read masking does not erase them.
- A permit also binds the exact configured website domain. Every actual domain change, including an edit between `example.com` and `www.example.com`, advances the collection generation and permanently invalidates old permits and backend keys, even if the domain later changes back. A no-op domain update does not advance the generation. Provision a new backend key for the new generation through the protected operator workflow. A tagged non-fragment external replay chunk stays pending until its sink acknowledges and the marker is confirmed; a concurrent retry receives a conflict, not false success. A definite pre-sink rejection removes the pending marker and atomically refunds only its visit reservation. The original source, account, and client attempt charges remain; each retry charges its current payload against all budgets. A process exit, an uncertain external outcome, or a failed marker confirmation leaves the chunk pending for reconciliation, never automatic replay. The Kafka oversized-message preflight is a definite no-send rejection. This does not establish exactly-once external persistence.

## Backend credential provisioning

The protected analytics runtime may define `COLLECTION_SERVER_KEYS_JSON` as a JSON object keyed by lowercase website UUID. Each value is an array of at most eight records of the form `{ "sha256": "<lowercase SHA-256 of a random credential>", "scopes": ["identity", "event", "revenue", "recorder"], "ownerType": "user", "ownerId": "<lowercase owner UUID>", "generation": 0 }`. `ownerType` may be `user` or `team`. The owner and generation must match the active website row exactly; legacy digest-only records are rejected. The forward-only migration initializes existing website generations to 0 and increments on each actual ownership transfer. Hard deletion retains the next generation in `website_collection_tombstone`, so administrator recreation of the same UUID cannot reactivate an old key. The tombstone is durable authorization state and must be preserved with the database through backup, restore, promotion, and rollback; never clear it to reuse a credential. A transfer invalidates old backend requests and recording permits, even if the site later returns to the same owner. Provision a new credential for the new owner through the protected operator workflow; do not automatically move the old credential. Review the retained runtime's migration-rollback compatibility before applying this migration to production. Use only needed scopes and distinct, independently revocable random credentials for every site. A raw credential must contain at least 32 random bytes encoded as 43-128 URL-safe characters, must remain on that website's backend, and must never enter browser JavaScript, a release artifact, source, chat, or logs. The analytics environment stores only digests. Missing or empty configuration permits startup but disables backend-authorized collection; a malformed nonempty configuration stops startup. The request boundary also rejects malformed configuration without printing its contents. Rotate or remove a digest to revoke it; do not share a credential across websites.

The standalone website, team, and user hard-delete paths all retain website generations before removing rows. Explicit site provisioning reads that retained generation before reusing a UUID. Shared collection writes and exclusive deletion/provisioning locks canonicalize UUID case, so mixed-case administrator input cannot bypass the generation check or an in-flight write. The protected operator must keep these paths together when reviewing a future adapter or data-recovery change.

The website backend, after authenticating its own user session, may submit identity or non-revenue custom events to the analytics collector with `Authorization: Bearer <credential>`, `X-Umami-Request-Id: <fresh random UUID>`, and `X-Umami-Request-Timestamp: <current Unix seconds>`. These headers are required for each advanced request, including a batch. The batch route derives a stable child ID from the parent ID, each item's JSON, and its occurrence among byte-identical items. Moving an item within a retry does not change its ID, while two identical items in one batch receive separate IDs. The collector accepts at most five minutes of clock skew and atomically reserves each ID in the PostgreSQL collection budget table. PostgreSQL collection persists in that same transaction; ClickHouse reserves before its external writes, so a partial external write requires reconciliation. The nonce persists for at least 15 minutes and is then eligible for bounded cleanup. Direct repeats within that window receive `409`; batch replies report a per-item `409` inside their HTTP `200` result. A later submission with a new timestamp after nonce expiry is a new attempt, not permanent deduplication. The backend must derive identity from its authenticated session and verify business facts before submission. It must not proxy arbitrary browser bodies or expose the credential through an endpoint, CORS, or the public tracker. A browser script receiving `403` for advanced tracking is the intended behavior until this integration is reviewed.

For definite HTTP rejection of an advanced browser call, the tracker dispatches `umami:tracking-error` on `window` with only the operation type and HTTP status. It does not expose the rejected payload or retry the call. A rejected identify or locally cancelled identify restores the preceding pageview session unless a newer accepted request supersedes it. Transport failures may have an uncertain server outcome and are not reported as confirmed rejections. Ordinary anonymous pageview failures remain silent.

Verified session identity is scoped to the website, the backend-supplied session or distinct identity, and the configured salt period, not the particular authorized credential digest. Credential rotation therefore does not intentionally split one verified session. A credential still grants only its declared website and scopes.

An identity-link write failure returns a bounded `503` rather than claiming success. In PostgreSQL mode the source transaction rolls back before session properties are saved. In ClickHouse mode a post-commit link-publication failure may leave accepted session properties; the caller must reconcile that uncertain partial outcome before retrying rather than infer exactly-once delivery from the response. The intentional link-history cap remains a separate admission outcome.

## Recorder opt-in

A site that deliberately enables recording must implement a same-origin, CSRF-protected endpoint. Enter its path in website replay settings; the copyable recorder snippet is withheld until a valid path is configured and then includes it as `data-permit-endpoint` on `recorder.js`. The endpoint receives the browser's public cache token and requested feature. It must independently verify the authenticated site session, feature-specific consent, and tenant identity. Only then may its backend call `POST /api/collection-permit` server-to-server with its recorder credential in `Authorization`, a fresh `X-Umami-Request-Id` and `X-Umami-Request-Timestamp`, the cache token in `x-umami-cache`, and `{ "website": "<UUID>", "feature": "record" | "heatmap", "origin": "<site origin>", "consent": true }`. Return only the `permit` to that browser. The analytics route checks the configured website domain, recorder feature, and strict replay masking before minting; it does not independently know whether the site's consent assertion is truthful. The recorder refreshes its permit every 15 seconds and stops capturing if refresh fails. Even if refresh stalls, the browser stops capture and removes heatmap listeners within 30 seconds of the last permit request. The server's signed permit expires within 60 seconds; immediate rejection requires rotating/removing the recorder key or disabling the feature.

Do not activate recorder capture just because a website has `recorderEnabled`: the site-owned session, consent, and permit endpoint must exist and pass acceptance first. Keep classroom collection disabled where already required.

## Required release and host acceptance

This contract must be delivered template-first and then reconciled into structurally compatible isolated forks, preserving each site's privacy configuration and database history. Test exact packaged bytes, ordinary pageviews, authorized identity/events, denied anonymous/batch claims, feature and origin mismatch, expired/revoked permits, strict replay masking, recorder cleanup, and both PostgreSQL and ClickHouse/Kafka persistence paths. No historical migration is rewritten. The production operator must review protected runtime key provisioning, site-backend integrations, version-aware rollback, and candidate acceptance before any promotion. Source publication alone is not activation.
