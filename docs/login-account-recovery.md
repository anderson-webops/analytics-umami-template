# Account-owned login recovery

This source candidate adds optional one-use codes for local analytics accounts. A saved active code permits its owner to attempt login while the shared username or source budget is exhausted. It does not replace the password, configured CAPTCHA, required two-factor verification, or the shared password-work limit. A wrong password spends the code, so it is an attempt credential rather than a reusable bypass. An owner with a current full session and current password can prepare replacement codes. A fully authenticated administrator can prepare them for another owner after confirming the administrator's current password. The protected operator tool described below is a separate recovery path. Each issuance shows plaintext once; the database stores digests only.

## Interrupted replacement and owner confirmation

HTTP preparation retains the active codes. It stores one bounded pending batch per owner for 15 minutes in `app_setting`, containing only code digests, bounded consumed-digest accounting, account/batch identity, expiry and current password/key fingerprints. Preparing another batch supersedes only the pending batch. Pending codes can admit bounded password/CAPTCHA/required-MFA attempts, preserving administrator-assisted recovery for an owner without a current session. They are not confirmed preparation and do not revoke the previous set.

The owner confirms a code from their saved copy with their own current full session, current password and explicit saved acknowledgement. Administrator delivery acknowledgement is not owner confirmation. The same transaction-time role, password, session-generation, Redis-revocation and current-factor checks protect preparation and confirmation. Partial, enrollment-only, API-key and share authority remain ineligible.

When no replacement batch is pending and no source confirmation receipt exists, that same owner confirmation can adopt a privately issued active batch. It spends only the supplied proof code and retains every other credential and its current password/key binding. At least one other unused code must remain. Concurrent confirmations serialize against consumption, and an interrupted transaction leaves the original codes intact. A pending replacement still requires its own saved-copy proof. Password changes continue to require a fresh pending batch.

A retry of an already recorded confirmation succeeds only while its exact password/key-bound batch still has an unused code. An exhausted batch retains its historical receipt and requires renewal; replaying its old confirmation cannot report usable recovery or restore spent codes. This source confirmation path preserves existing issued batches and does not replace accepted protected owner-rollout evidence.

The HTTP contract explicitly selects `action: "prepare"` or `action: "confirm"`. Older clients that assume immediate rotation fail validation rather than silently receiving expiring pending codes as an active replacement. The maintained UI and generated API client use the new contract together. Existing active codes and protected operator issuance retain their previous login behavior.

Confirmation atomically replaces the active credentials with unused codes, excluding the proof and previously spent pending codes, removes the pending batch and records nonsecret exact-batch confirmation. At least one unused code must remain. A row lock serializes confirmation with pending-code consumption so a raced spent credential cannot become unused again. A lost confirmation response can be retried with the same proof and current authentication without restoring spent codes or rotating again. A stale, expired, wrong-owner, wrong-batch, changed-password or changed-key proof cannot activate replacements. The UI announces activation only after the server confirms it; its checkbox alone is not durable preparation.

This source-side confirmation records this application's workflow, not a new claim about independently completed production-owner checks. Existing real-owner confirmations and working active credentials are retained. No existing owner is re-provisioned by this change. The protected lost-code issuer remains independent and immediately replaces credentials; it clears source pending/confirmation metadata rather than manufacturing owner proof.

One of the existing four shared password-verification slots is reserved for requests with a verified account-owned code. Ordinary requests can use the other three; verified recovery requests can use any of the four. Source-admission storage failures and invalid counter responses return HTTP 503 before code lookup, consumption, or password work. Exhausting the bounded in-process counter capacity remains a quota condition, so a valid saved code can still provide recovery without increasing the total work limit.

The codes are bound to the account, its current password credential, and the signing-key fingerprint. Ordinary logout does not revoke them. A password change, account deletion, or rotation of the application's `APP_SECRET` makes existing codes unusable. The status endpoint excludes codes from an old key. Automatic password-hash upgrades rebind unused codes in the same transaction; plan secret rotation and code reissuance together. Do not log or export plaintext codes.

A fully authenticated administrator who confirms their own current password can prepare replacement codes for a different active account. The target's password and two-factor requirement remain unchanged. The owner can confirm privately received codes in Security without generating a different batch. Preparation and delivery are not proof of owner possession. A stale administrator session, revoked factor, deleted target, or changed target password cannot authorize or preserve those codes.

## Self-service password changes

For local accounts, the password form prepares replacement recovery codes before saving a new password. The owner saves that batch and supplies one unused code with `saved: true` to `/api/me/password`. A current full session and current password remain required. One transaction confirms the fresh pending batch, updates the password and session generation, revokes prior sessions and API keys, and binds the unused replacement codes and confirmation receipt to the new password. The proof code and previously spent pending codes remain spent. The previous password and active codes remain unchanged if preparation is cancelled or activation fails.

An expired, superseded, wrong-owner or changed-key batch cannot change the password. An earlier confirmation receipt cannot replace fresh pending proof, including when all its codes have been exhausted. A lost successful response leaves the saved unused codes available with the new password. Verified MFA is retained on the replacement session. Automatic bcrypt rehashing continues to preserve current recovery without changing the password; administrator resets and protected key transitions keep their separate lifecycle requirements. Cloud retains its existing password API contract because local login recovery is unavailable there.

## Protected operator bootstrap and lost-code recovery

The runtime artifact must contain both migration `41_add_login_recovery_credentials` and `runtime-scripts/issue-login-recovery.mjs`. Capability `protected-login-recovery-issuance-v1` requires the server operator to review a TTY-only, non-root, Linux ARM64 process using the protected service environment and the exact verified runtime artifact, never a mutable checkout or a privileged root process. The host must verify the intended database and target user ID independently before invoking the packaged tool with `--user-id`. The tool requires the operator to type the target's exact username and rejects deleted or changed targets; it rotates all previous codes transactionally. It has no HTTP endpoint and does not change the target's password or two-factor status.

The operator must verify the owner's identity and deliver codes privately without terminal recording, shell history, or logs containing the codes. The owner should prove possession through one successful password/CAPTCHA/two-factor login with a code, leaving the other codes unused. Record only nonsecret user IDs, counts, and acceptance results. If output is interrupted or exposure is suspected, rotate again; never try to recover plaintext from the database. Use this process for the initial administrator and for an owner with no usable codes. Source agents cannot perform these production actions.

## Rollout and remaining risk

The migration creates an empty credential table. It cannot securely issue codes to existing owners without a verified session or the reviewed protected operator process. **An owner who has not saved codes can still be locked out by distributed failed login attempts for the configured window until an operator intervenes.** A successful code login does not erase the shared account-attempt budget; ordinary password-only login may remain unavailable until that window expires, although an owner with a full session can rotate unused codes. The source-level targeted-lockout finding is not resolved for an unprovisioned owner. Do not count rollout complete until every applicable active owner has a verified recovery path, including the initial administrator, and the protected lost-code procedure is accepted. CAPTCHA alone is not account ownership proof.

Migration `41_add_login_recovery_credentials` is forward-only in the release ledger. The retained pre-migration runtime may reject a database containing its new ledger entry. A pointer-only application rollback is therefore not a recovery plan. Before production migration, the server operator must rehearse upgrade and failed-activation recovery on a protected copy, retain a quiesced pre-migration database backup and the exact prior runtime/policy, and approve a database-aware restore procedure. Source publication is not production activation.

## Source verification

The focused tests cover owner-only issuance, current-password and session checks, denied-code admission, single-use concurrency, password-hash upgrade, password change, logout, deletion, and no-store responses. The disposable PostgreSQL 17 fixture applies the exact new migration SQL and checks real concurrent consumption, cascade deletion, and the administrator HTTP issuance route with wrong-password, non-administrator, and downgraded-administrator denials. It also exhausts account and source admission, verifies that a saved code permits the owner's correct-password login while an ordinary login is denied, rejects reuse and wrong passwords, and preserves configured CAPTCHA verification under an occupied overflow lease. The default PostgreSQL restore runner includes that fixture. Exact clean Linux ARM64 packaging, retained-runtime recovery, downstream site adoption, and protected production acceptance remain separate release gates.
